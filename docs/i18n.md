# 界面语言

Candlewick 说三种语言：English、简体中文、日本語。托盘 / 任务栏和下拉菜单、macOS 的应用菜单、窗口标题、错误与状态说明、三个窗口的页面，全部跟着同一个语言走。

## 谁决定语言

Rust 决定，页面只跟随（`src-tauri/src/i18n.rs`）。

- 设置 → 通用 → 语言：「跟随系统」或三种之一，存在 `Settings.language`（`system`、`en`、`zh-CN`、`ja`）。
- 跟随系统时，取系统首选语言列表里第一个应用会说的（`sys-locale`：macOS 是 `CFLocaleCopyPreferredLanguages`，会读到「系统设置 → 通用 → 语言与地区 → 应用程序」里单给 Candlewick 选的语言；Windows 是显示语言列表）。繁体中文不算简体中文，和系统匹配 bundle 本地化时一样，交给列表里的下一个语言；都不会说就用英文。
- `Language` 是 `System` 或 `Only(Locale)`，写进设置文件和发给页面时就是 `system` 或语言标签。
- 启动时先定语言再建托盘；改设置时 `save_settings` 依次：记下语言（macOS，见下文）、切换、`window::relabel`（改窗口标题、给每个页面发 `locale` 事件、重建 macOS 应用菜单）。托盘菜单的 `Layout` 带着语言，语言一变下次绘制就整份重建；Windows 的下拉菜单开着时不换，等下次打开。

## 文字放在哪

| 目录 | 谁说 | 写法 |
|---|---|---|
| `src-tauri/locales/<tag>.json` | Rust：托盘与菜单、应用菜单、窗口标题、错误、状态说明；外加 `common`，即页面也要用的词：数据源名、总资产、24h 盈亏、多空、更新于、正在读取 | `t!("tray.quit")`、`t!("common.holdings.updated", time = clock)` |
| `src/locales/<tag>.json` | 三个窗口的页面 | `const { t } = useTranslation()`，`t("settings.title")` |

页面通过具名 JSON 导入拿 `common`（`src/lib/i18n.ts`），打包时只带这一段，Rust 的错误文字不会进页面。

约定，两边一样：

- 占位符写作 `%{name}`。
- 两个平台说法不同的消息，Windows 那句加 `_windows` 后缀（「菜单栏」与「任务栏」）。页面用 `t(key, PLATFORM)`；Rust 只写 `t!("error.onePinned")`，`build.rs` 按编译目标把对应的那句编进去。
- 英文的复数用 `_one` / `_other`，i18next 按 `count` 和语言的复数规则选；中文、日文只写 `_other`。Rust 侧的文字不用复数，措辞绕开它（`Others (3)`）。
- 随数据变的说法用 i18next 的 context：`t("chart.high", { context: spec.statsSpan })` 读 `chart.high_rolling24h` 或 `chart.high_today`。
- key 是 camelCase，`_` 只用来接复数、平台和 context。
- 语言名永远用它自己的写法（English、简体中文、日本語），不翻译；语言那一行带通用的语言图标，看不懂当前语言也找得到。

## Rust：编译出来的 `t!`

`build.rs` 把 `src-tauri/locales/*.json` 编译成 `t!` 宏（每条消息一条规则）和每条消息一个函数，按当前语言返回：没有占位符的是 `&'static str`，有的是 `format!` 出来的 `String`。所以数据源名、交易时段、菜单分区标题这些词和翻译前一样是静态字符串，托盘每秒重绘不为它们分配内存。占位符按英文里出现的顺序写。于是：

- key 写错、占位符名写错或漏写，都编译不过，报错直接说 `locales/en.json has no message "…" with these placeholders`；
- 某语言缺一条、多一条，或占位符和英文不一致，构建失败；
- 运行时没有查表，也没有依赖。

同一个 `build.rs` 也检查页面的目录（`src/locales/`，i18next 原样读取，不生成代码）：规则相同，只是允许复数形式，各语言按自己的复数规则写。两套目录的问题都在 `cargo build`（也就是 `tauri dev` / `tauri build`）时报出，不用等测试。目录里有哪些语言由文件决定，`zh-CN.json` 对应 `Locale::ZhCn`。

没有用 rust-i18n：它的 4.x 需要 `toml` 0.8.8 以上，而 Tauri 的 Linux 依赖链（gtk → glib-macros → proc-macro-crate 2.0.2）把同一个 lockfile 里的 `toml` 锁在 0.8.2，解不出可用的组合；它对写错的 key 也只在运行时原样显示 key。

只进日志的文字（重连原因、路由）用英文，不进目录。

## 页面：i18next

- `src/lib/i18n.ts` 初始化 i18next 和 react-i18next，三种语言一起打包，切换即时，不等加载。
- 页面加载时先订阅 `locale` 事件，再用 `get_locale` 问应用当前的语言，问到了才渲染第一帧（窗口本来就等页面报告就绪后才显示，不会闪）。语言只有 Rust 那一份，页面无论何时加载、重新加载，说的都是应用此刻的语言。`<html lang>` 随之改变。
- 语言清单在 `src/lib/i18n.ts` 的 `LOCALES`（标签 → 它自己的名字），`Locale` 类型、i18next 的 `supportedLngs`、设置页的选项都从它来。
- key 由 TypeScript 检查：`src/i18next.d.ts` 从英文目录推出全部 key，写错就编译不过。
- `useTranslation` 返回的 `t` 在语言变化时换成新的，React Compiler 的缓存以它为依赖，所以切换语言不需要重新挂载，行情窗口的推流也不断。组件外的辅助函数（`insight`、`allocation`、`intervalLabel`）把 `t` 当参数传入；不要在模块顶层调用 `t`，那样的文字不会跟着语言变。

## 数据不带文字

Rust 发给页面和 AI 接口的是代码，由显示它的一方翻译：钱包（`spot`、`usdFutures`…）、合约类型（`usdtPerpetual`、`coinFutures`…）、`sizeUnit` 为 null 表示张数、交易时段（`pre`、`post`、`overnight`）、K 线周期只给秒数、`statsSpan`（`rolling24h` 或 `today`）、行情窗口的 `source` 是数据源 id、`link` 只有地址。AI 接口自己的拒绝信息是英文，接口不随界面语言变。

例外是成句的说明：错误信息、搜索的 `notes`、长桥给的行情包名和提示。它们在 Rust 里产生时按当时的语言写好；长桥的请求带 `accept-language`（中文界面 `zh-CN`，其余 `en`），股票名在中文界面取中文名、其余取英文名（添加时取，存在自选里）。

## 数字、时间与字体

- 价格、数量和时钟在各语言里写法一样（`84,049.95`、`14:03:27`），和托盘一致。
- 用词的部分按语言，用 `Intl`：紧凑单位（`1.23万`、`12.35K`）、「近 1 小时」的时长、浏览历史时的日期区间（`formatRange`，各语言自己的连接符）、AI 助手名单的列举。
- 日文页面先用日文字体（`index.css` 的 `html:lang(ja)`：macOS 用 Hiragino，Windows 用 Yu Gothic UI），汉字不会显示成中文字形；Windows 任务栏行情条的 DirectWrite 回退字体也按语言选。

## 系统自己的文字

- macOS：`Info.plist` 声明 en、zh-Hans、ja，输入框右键菜单、关于面板这些系统文字能跟系统语言。设置里选了具体语言时，应用把它写进自己的 `AppleLanguages`，等同于在系统设置里给 Candlewick 选语言，下次启动起系统文字也换过去；选「跟随系统」就清掉。只在用户改设置时写，启动时不碰，免得覆盖用户在系统设置里的选择。
- Windows：安装程序有英文、简体中文、日文，按系统语言显示，不认识的系统语言用英文。

## 加一条文字

三个语言的文件同时加。三种语言齐全、占位符和英文一致由构建检查（见上）；页面里的 key 由 `tsc` 检查。`cargo test` 的 `i18n::tests` 再查一件事：两个目录里的每条消息都有代码在用（Rust 里的 `t!("…"`，页面里的字面量 key，或模板字符串的前缀如 `` `holdings.wallet.${…}` ``）。页面调用 `t` 时传的占位符没有编译期检查，写错会在界面上原样显示 `%{name}`。

## 加一种语言

1. `src-tauri/locales/` 和 `src/locales/` 各加一个文件。
2. `i18n.rs`：`Locale` 加变体（和 `ALL`），`Locale::matching` 认它的系统标签。之后编译器会指出每个要为它做决定的 `match`：macOS 的 `remember_language`、Windows 的 DirectWrite 语言名、币安和 OKX 的链接、长桥的 `language()`。
3. `src/lib/i18n.ts` 的 `LOCALES` 和 `resources`。
4. 打包：`Info.plist` 的 `CFBundleLocalizations`、`tauri.windows.conf.json` 的 NSIS 语言；需要的话 `index.css` 加字体，设置页 `apiPage` 的链接。

## 在浏览器里看

`pnpm dev` 后在地址上加 `?lang=en`、`?lang=zh-CN` 或 `?lang=ja`；不加时按浏览器语言（`src/dev/mock.ts`）。

## 已知限制

- 切换语言后，已经产生的成句文字保持原来的语言：页面上正显示的 Rust 报错、账户的 `error`、长桥的行情包名，等下一次刷新才换；自选里股票的名字是添加时取的，要重新添加才换。
- 长桥没有日文，日文界面下股票名和长桥的提示是英文。
- 繁体中文系统上（之后的首选语言也不是英文、中文、日文时）界面是英文。

## 现状

这一节记录引入多语言这一轮的实现情况，随后续改动更新。

- Tauri 本身没有运行时的 i18n：它只管打包层（NSIS 安装包语言、Info.plist 的 `.lproj` 本地化）和 `tauri-plugin-os` 的 `locale()`（只给一个系统语言，内部就是 sys-locale）。界面文字由应用自己做，所以选了前端 i18next、Rust 侧 build.rs 生成。
- 英文和日文译文由实现这一轮的模型撰写，没有经过母语者校对；中文沿用原有文案。外链里 OKX 日文界面不加前缀已核对（`/ja/…` 会 301 回不带前缀的地址）；币安的 `/ja/` 路径没能核对，它对脚本请求一律返回验证页。
- 顺带删掉了设置窗口状态行的后端（`get_status` 命令、`status` 事件、`StatusView`、`Status::label`、`Status::tone`，以及只为它存在的 `Status::Live` 里的路由、`Status::Retrying` 里的原因）：状态行的界面在 30a61fe 已经移除，这些文字原本也要翻译。连接的路由和重连原因仍然进日志。
- 验证到的程度：`tsc` 与 `vite build`；macOS 与 Windows（`cargo xwin clippy`）的 clippy 无警告；`cargo test` 的单元测试；`macos_bar` 原生测试，含切到日文后托盘菜单与子菜单分区标题整份重建。目录检查用故意的破坏试过：页面目录缺一条、页面或应用目录的占位符写错、`t!` 的占位符写错，都在构建时报出。在浏览器里（`pnpm dev` 的 mock）把持仓页从英文切到日文再切到中文，文字全部跟着换，页面没有重新挂载；设置页在 460 宽下三种语言都没有被截断或溢出的文字（mock 里没有 API Key 和长桥两栏的内容）。
- 没有验证的：没有启动应用，所以没有走过 `get_locale` 命令和 `locale` 事件的真实链路，也没有在应用里切换过语言；行情页和持仓页侧栏的排版没有逐个语言看过；`AppleLanguages` 写入后下次启动系统文字是否跟着变；Windows 版只做了编译和 clippy，没有运行；NSIS 的日文安装界面只能在 Windows CI 上出包时看到。
